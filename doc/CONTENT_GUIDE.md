# 内容维护指南

## 换成自己的旅行档案

个人内容统一放在 `data/`，复用项目时按以下步骤替换：

1. 用自己的 PNG 头像替换 `data/profile/profile-picture.png`，保留文件名即可。
2. 将旅行记录写入 `data/travel_data.json`，正文放入 `data/travel-diary/YYYY/`，照片放入 `data/photos/`，并同步记录中的路径。不保留任何记录时使用空数组 `[]`。
3. 删除不再使用的示例日记和照片，避免它们仍随静态站点发布。
4. 字体源文件发生变化时，按 [资源维护规范](ASSET_MANAGEMENT.md) 运行 `npm run fonts` 更新本地完整字体，再运行 `npm test` 并检查页面。

`assets/catalogs/countries.json` 是共享参考目录，复用项目时保留完整文件；无需按自己的旅行范围删减国家，也无需修改页面代码或通用背景素材。

## 新增旅行记录

### 页面编辑器

在项目根目录运行 `npm start`，通过本机 localhost 地址打开页面。点击头部「＋」或旅行路径页的「新增旅行记录」，输入 6 位数字密码后进入编辑器。验证界面同时支持实体键盘：数字键输入，Backspace / Delete 删除，Enter 确认，Esc 关闭。窄屏设备可使用旅行路径页入口。

访问密码保存在 `data/password.json` 的 `password` 字段中，格式为 6 位数字字符串。页面每次验证都会重新读取该文件。密码会随静态站点和全部数据备份发布，只用于避免访客误入编辑或导出流程，不是服务端认证，也不会加密个人数据。

编辑器按内容组织，并提供独立的文件设置：

| 区域 | 内容 |
| --- | --- |
| 行程与地点 | 日期、旅行标识、国家 / 地区、一级行政区、目的地及可选类型。 |
| 旅行正文 | 日记标题、带语法高亮的可编辑 Markdown 源码与可编辑的渲染预览。 |
| 旅行照片 | 本地图片选择与拖放、缩略图、顺序调整和移除。 |
| 文件设置 | 自定义正文路径及已有项目照片引用，默认折叠。 |

日期、国家 / 地区、目的地和日记标题为必填项。国家显示名称随国家选择填入，允许自定义；留空时使用国家目录名称。其他字段为选填，字段定义见下文。

地点字段支持关联候选和可靠补全。选择国家后，行政区、目的地和类型候选会按当前地点范围收窄。中国目的地会优先从 `assets/catalogs/china-locations.json` 反查省级行政区，支持省略常见的“市”“县”等后缀，例如填写“衡阳”或“衡阳市”都会补全“湖南省”，填写“大理市”或“建水县”会补全“云南省”。跨省重名地点在无法唯一判断时不会强行填写。目录外地点继续使用个人历史记录补全；新地点仅根据明确后缀判断类型，例如中国的“省”“自治区”“直辖市”、日本的“都 / 道 / 府 / 県”，以及“市”“岛”“群岛”“国家公园”。自动填写的内容可直接修改，手工改动后不会再被覆盖。

旅行标识用于把多篇日记归入同一次旅行。编辑器会优先根据完整日期和目的地自动填写，未填写目的地时回退到行政区，格式为 `YYYY-MM-DD-pinyin`，例如 `2026-09-07-hengyang`。日期或地点变化时，尚未手工修改的自动值会同步更新；手工修改后不再覆盖。下拉候选按最近日期倒序列出 5 个不同的已有行程，便于同一次旅行的后续日记沿用标识。保存时，手工输入的中文标识也会转成小写、无声调拼音。正文路径和所选照片目录会在「文件设置」中预览，留空即可使用自动值。

单行字段最多 200 字符，正文最多 100000 字符；已有照片列表最多 1000 项，每个文件名最多 200 字符。可选择 JPEG、PNG、GIF 和 WebP 图片，应用不另设张数或文件大小上限；实际容量取决于浏览器内存、磁盘空间和本机读写速度。

「保存旅行记录」创建 Markdown 文件并更新 `data/travel_data.json`。保存完成后，旅行路径页重新加载记录和统计。线上站点的内容更新需提交并推送相关文件。

### 正文视图与草稿

| 操作 | 输出或行为 |
| --- | --- |
| 源码 | 直接编辑带语法高亮的完整 Markdown，第一行一级标题与日记标题字段同步。 |
| 预览 | 在渲染结果上直接修改文字；工具栏支持粗体、斜体、标题、段落和列表。 |
| 导出草稿 | 下载 ZIP 草稿；`draft.json` 包含字段，所选图片保存在 `photos/` 中。 |
| 导入草稿 | 读取 ZIP 草稿并填入表单；也兼容旧版 v1、v2 和 v3 JSON。导入后需另行保存。 |

源码与预览双向同步，切换视图保留已输入内容。预览中选中文字后可设置格式，支持浏览器原生撤销与重做；粘贴内容按纯文本插入。键盘方向键、Home 和 End 可切换正文标签。预览修改后会按支持的 Markdown 结构重新序列化，空行和样式标记可能规范化；表格、代码块和嵌套列表等不支持的结构应保留在源码中编辑。

ZIP 草稿中的 `draft.json` 不是旅行索引，不能替换 `data/travel_data.json`。所选照片以独立文件存放在 ZIP 中，导入后恢复原图和顺序；已有项目照片仍依赖原路径。编辑器也兼容旧版 v1 至 v3 JSON 草稿，缺失的可选字段按空值处理。为避免误覆盖，当前页面有未保存内容时不会导入另一份草稿。

未保存草稿仅保留在当前页面内存中。关闭编辑器后可以继续编辑；刷新或离开页面前应保存或导出草稿。

### 正文路径与照片引用

正文路径留空时按以下格式生成：

```text
data/travel-diary/YYYY/YYYY-MM-DD-pinyin.md
```

目的地会去除常见行政区后缀并转成小写、无声调拼音，例如“苏州市”默认生成 `data/travel-diary/2026/2026-09-11-suzhou.md`，“重庆市”生成 `2026-09-11-chongqing.md`。自定义路径必须保留与旅行日期一致的年份目录和日期前缀。文件名、照片目录和照片文件名仅允许 ASCII 字母、数字、连字符、下划线和点，禁止路径穿越和系统保留名称。保存不会覆盖已有正文；相同路径、元数据和正文的重复提交返回已保存状态。

「选择照片」支持多选，也可将图片拖入指定区域。缩略图下方可调整顺序或移除照片。保存记录前，所选图片只保留在当前浏览器页面中。

保存时，新照片自动写入 `data/photos/pinyin/`。文件名主体由原文件名转成小写、无声调拼音，扩展名以实际图片格式为准；重名时追加 `-2`、`-3` 等序号。应用会自动填写 `photo_folder` 和 `photos`，顺序与缩略图一致。原始图片字节保持不变，不会压缩或裁剪。

### 全部数据导入与导出

个人主页右侧「数据备份」提供以下操作：

- 「导出全部数据」使用与新增记录相同的 6 位密码验证，然后下载 `travel-diary-data-YYYY-MM-DD.zip`。本机页面按当前 `data/` 内容即时生成；GitHub Pages 下载最近一次部署时生成的备份。
- 「导入全部数据」先要求输入当前 `data/password.json` 的 6 位密码，浏览器通过后，本地服务还会在数据锁内再次核对该密码。授权成功后才接受本应用导出的 ZIP，并校验 ZIP 完整性与路径、旅行索引 JSON、记录字段和日期、正文路径与 UTF-8 内容、照片目录及引用、密码配置，并拒绝仅大小写不同的冲突路径；全部通过后才用临时目录原子替换当前 `data/`。

当前密码用于授权覆盖现有数据，备份内密码不参与这一步授权：备份文件本身可能被复制，并不能证明操作者有权修改当前档案。备份中已经包含密码时，导入后会使用该密码；如果备份缺少 `data/password.json`，页面会在其他数据校验通过后提示设置新的 6 位数字密码，并要求再次输入确认。新密码随本次导入写入 `data/password.json`；取消设置会终止导入，当前数据保持不变。

通用静态服务器需要先运行 `npm run data:archive`，再把 `dist/travel-diary-data.zip` 作为站点根目录的 `travel-diary-data.zip` 发布。导入会写入并完整替换 `data/`，因此仅支持本机 localhost 页面；操作前务必导出当前备份。缺少密码、取消密码设置、校验失败或导入失败均不会修改现有数据。ZIP 使用标准 UTF-8 文件名和无加密存储格式，空目录不会单独写入。

「文件设置」中的照片目录和列表用于引用项目中已经存在的文件，照片目录限定在 `data/photos/` 下。存在新选择的照片时，已有照片会按需复制到目的地目录并排在新照片之前，原文件保持不变；若来源就是该目的地目录则直接复用。仅引用已有照片时不创建新目录。

保存失败会清理本次创建的照片文件与空目录。请求结果不确定时，使用原草稿重试，服务器核对元数据、正文和照片字节，避免重复创建或覆盖其他文件。

### 静态托管与离线使用

| 环境 | 编辑与导出 | 保存到项目文件 |
| --- | --- | --- |
| 本机 `npm start` 与 localhost 地址 | 支持，断网可用 | 支持 |
| GitHub Pages 或通用静态服务器 | 页面资源加载后支持 | 不支持 |
| 本项目服务器的局域网访问 | 支持 | 不支持，仅本机可写入 |

只读环境仍可编辑记录、选择照片并导出 ZIP 草稿，也可下载当前站点的完整数据备份。要写回项目文件，请在本机编辑器导入草稿，核对后保存。草稿或数据导出不会修改站点，也不会触发发布。

本项目的离线运行依赖本机服务器与仓库内资源。线上页面未配置 Service Worker 缓存，不保证断网后的首次访问或刷新可用。

保存失败时表单内容保持不变。若请求超时，服务器可能已完成写入，应使用原路径和原内容重试。数据文件损坏、权限异常及写入锁恢复参见 [维护与发布指南](MAINTENANCE.md#写入故障恢复)。

### 手工新增

1. 在 `data/travel-diary/YYYY/` 新建 Markdown 文件。
2. 在 `data/travel_data.json` 添加一条记录。
3. 运行 `npm test`。
4. 启动 `npm start`，在浏览器检查首页、旅行路径和日记详情。

推荐文件名：

```text
data/travel-diary/YYYY/YYYY-MM-DD-slug.md
```

示例：

```text
data/travel-diary/2026/2026-07-11-suzhou.md
```

## 元数据字段

`data/travel_data.json` 是数组，每一项代表一篇旅行日记。

| 字段 | 类型 | 必需 | 说明 |
| --- | --- | --- | --- |
| `date` | string | 是 | 日期，格式为 `YYYY-MM-DD`。 |
| `country` | string | 是 | 面向读者显示的国家或地区名称。 |
| `country_code` | string | 是 | ISO 3166-1 alpha-2 两位代码，用作稳定的国家标识，例如 `CN`、`US`、`JP`。 |
| `admin_area` | string | 否 | 一级行政区名称。可表示州、省、大区、都道府县、自治区等；城市国家或不需要该层级时可以省略。 |
| `admin_area_type` | string | 否 | 一级行政区类型覆盖值，例如 `州`、`省`、`都`。常见国家会自动提供界面标签，只在需要更精确说明时填写。 |
| `locality` | string | 是 | 实际目的地，不限于城市，也可以是村镇、岛屿、景区或其他地点。 |
| `locality_type` | string | 否 | 目的地类型，例如 `城市`、`岛屿`、`国家公园`。 |
| `trip_id` | string | 否 | 小写拼音旅行标识。编辑器默认按完整日期和目的地自动填写；同一次旅行包含多篇日记或多个目的地时，应从最近行程候选选择同一个值，用于按旅行去重计算到访次数。 |
| `desc_md` | string | 是 | Markdown 正文路径，相对项目根目录。 |
| `photo_folder` | string | 否 | 照片目录，相对项目根目录。 |
| `photos` | string[] | 否 | 照片文件名列表，与 `photo_folder` 拼接成图片路径。 |

示例：

```json
{
  "date": "2026-07-11",
  "country": "中国",
  "country_code": "CN",
  "admin_area": "江苏省",
  "locality": "苏州市",
  "trip_id": "2026-07-11-suzhou",
  "desc_md": "data/travel-diary/2026/2026-07-11-suzhou.md",
  "photo_folder": "data/photos/suzhou",
  "photos": ["canal.jpg", "garden.jpg"]
}
```

每篇记录都会按日期从早到晚获得行程编号，最早的行程为 1；记录卡片右侧和日记详情会显示同色同号的“行程”色签。如果同一次旅行去了同一省的多座城市，应为这些记录填写相同的 `trip_id`。例如南京和苏州属于同一次江苏旅行时，两篇记录都填写 `"trip_id": "2024-11-jiangsu"`，它们会共用同一个行程编号，并将江苏省计算为 1 次到访。色签编号仅用于界面分组，不展示原始 `trip_id`；未填写 `trip_id` 的旧记录会各自获得独立编号。

## 不同国家和特殊地区

一级行政区统一写入 `admin_area`，界面会根据 `country_code` 使用适合该国家的名称。例如美国显示“州 / 特区”，日本显示“都道府县”，加拿大显示“省 / 地区”；未配置的国家回退为“一级行政区”。

美国州：

```json
{
  "country": "美国",
  "country_code": "US",
  "admin_area": "California",
  "admin_area_type": "州",
  "locality": "San Francisco"
}
```

日本都道府县：

```json
{
  "country": "日本",
  "country_code": "JP",
  "admin_area": "東京都",
  "locality": "東京"
}
```

城市国家可以省略 `admin_area`：

```json
{
  "country": "新加坡",
  "country_code": "SG",
  "locality": "新加坡"
}
```

系统仍能读取旧内容中的 `province` 和 `city`，旧版 `province/city` 路由也会自动转换；新增内容应统一使用新字段。

## 国家目录

`assets/catalogs/countries.json` 是应用使用的通用国家目录，与个人旅行记录分开维护，当前包含 ISO 3166-1 的 249 个国家、属地及特殊地理区域。每一项包含：

- `code`：ISO alpha-2，两位代码。
- `alpha3`：ISO alpha-3，三位代码。
- `numeric`：ISO 三位数字代码。
- `name_zh`、`name_en`：Unicode CLDR 提供的简体中文和英文名称。
- `aliases`：常用简称或名称变体，可用于旧内容兼容和国家识别。
- `admin_area_label`、`admin_area_option`：一级行政区在界面中的称谓。
- `admin_area_optional`：该国家或区域是否通常可以省略一级行政区。

旅行记录中的 `country_code` 必须能在该目录中找到。常见行政体系会显示具体称谓，例如“州 / 特区”“省 / 地区”“都道府县”“酋长国”；未单独配置的国家统一回退为“一级行政区”，不会错误地假设为省。

国家目录由 `scripts/update-countries.mjs` 生成。需要同步 Unicode CLDR 数据时：

```bash
npm run countries
npm test
```

生成脚本固定 CLDR 版本，避免每次安装或启动时访问外部网络。不要直接在运行时代码中新增国家表。

## 中国省市区目录

`assets/catalogs/china-locations.json` 保存中国大陆 31 个省级行政区，以及对应的地级目的地和区县名称。新增记录时仅当 `country_code` 为 `CN` 才会使用该目录：

- 根据目的地唯一反查 `admin_area` 和 `admin_area_type`。
- 在行政区和目的地下拉候选中补充完整省、市信息，个人历史记录仍排在前面。
- 同名地点对应多个省份时保持为空，等待手工选择行政区。
- 香港、澳门和台湾继续按国家目录中的 `HK`、`MO`、`TW` 独立处理。

目录由 `scripts/update-china-locations.mjs` 从固定版本的 `cn-division` 生成，数据来源与许可信息记录在目录元数据及 `THIRD_PARTY_NOTICES.md` 中。需要更新时运行：

```bash
npm run china-locations
npm test
```

生成结果会随仓库分发，页面运行时不访问外部服务，因此离线新增记录仍可使用自动补全。

## Markdown 写法

正文建议以一级标题开头：

```markdown
# 苏州一日

## 平江路

雨后的石板路很安静，沿河的茶馆开得很早。

- 适合步行
- 适合拍照
- 傍晚灯光更好
```

当前解析器支持：

- `#` 到 `######` 标题。
- `- ` 无序列表。
- 段落和换行。
- 行内链接、粗体、斜体、删除线、标记、上标、下标和行内代码。

当前解析器不支持表格、代码块、HTML 块和嵌套列表；需要这些能力时，应先扩展 `js/data.js` 并补充测试。

## 照片

没有照片时可省略 `photo_folder` 和 `photos`，也可保留空列表：

```json
"photo_folder": "data/photos/suzhou",
"photos": []
```

如果添加照片，建议创建：

```text
data/photos/suzhou/
├── canal.jpg
└── garden.jpg
```

然后在记录中写：

```json
"photos": ["canal.jpg", "garden.jpg"]
```

图片文件名使用小写英文、数字和连字符，避免空格与中文文件名，便于部署到静态托管平台。

## 内容检查

提交前检查：

- `desc_md` 指向的 Markdown 文件存在。
- `photos` 中每个文件都存在于 `photo_folder`。
- 日期格式为 `YYYY-MM-DD`。
- `country_code` 是有效的两位大写代码。
- `locality` 已填写；`admin_area` 是否填写应以当地行政层级为准，不要为了满足层级而重复国家名。
- 同一次旅行的多篇记录使用完全相同的 `trip_id`，不同旅行不要复用同一标识。
- 同一天多篇日记时，文件名 slug 必须不同。
- 运行 `npm test` 通过。
