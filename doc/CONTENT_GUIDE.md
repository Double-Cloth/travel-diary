# 内容维护指南

## 换成自己的旅行档案

个人内容统一放在 `data/`，复用项目时按以下步骤替换：

1. 用自己的 PNG 头像替换 `data/profile/profile-picture.png`，保留文件名即可。
2. 将旅行记录写入 `data/travel_data.json`，正文放入 `data/travel-diary/YYYY/`，照片放入 `data/photos/`，并同步记录中的路径。不保留任何记录时使用空数组 `[]`。
3. 删除不再使用的示例日记和照片，避免它们仍随静态站点发布。
4. 字体源文件发生变化时，按 [资源维护规范](ASSET_MANAGEMENT.md) 运行 `npm run fonts` 更新本地完整字体，再运行 `npm test` 并检查页面。

`assets/catalogs/countries.json` 是共享参考目录，复用项目时保留完整文件；无需按自己的旅行范围删减国家，也无需修改页面代码或通用背景素材。

## 管理旅行记录

### 页面编辑器

在项目根目录运行 `npm start`，通过本机 localhost 地址打开页面。默认 write mode 为 `local`，本机可写、远程访问只读。也可由管理员显式启用 remote write mode 后，通过局域网地址或同站点域名写入。点击头部「＋」或旅行路径页的「新增旅行记录」，输入服务器访问口令后进入编辑器。输入框支持密码管理器、粘贴和实体键盘，Enter 确认，Esc 关闭。窄屏设备可使用旅行路径页入口。

访问口令不保存明文。运行 `npm run auth:set` 后，脚本在不回显输入的交互式终端中生成随机盐和 `scrypt` 哈希，并原子写入 `.secrets/auth.json`。口令要求 16–128 个字符且不能是低多样性重复值，建议由密码管理器生成至少 20 个随机字符，或使用多个无关单词组成的长口令短语。认证只在服务端进行；浏览器不能下载认证配置，也不能读取 `HttpOnly` 会话 Cookie。

仓库中的兼容配置仍可用旧 6 位口令完成 localhost 本机迁移，但标记为 `productionReady: false`，服务器会拒绝以 remote write mode 启动。设置强口令后可按需提交新的哈希配置；哈希不是加密，公开仓库会让攻击者进行离线猜测，因此生产仓库应限制访问并使用真正的随机强口令。公网还应使用 HTTPS，并建议配置反向代理认证、VPN 或 Zero Trust 作为第二层保护。

编辑器按内容组织，并提供独立的文件设置：

| 区域 | 内容 |
| --- | --- |
| 行程与地点 | 日期、旅行标识、国家 / 地区、一级行政区、目的地及可选类型。 |
| 旅行正文 | 日记标题、带语法高亮的可编辑 Markdown 源码与可编辑的渲染预览。 |
| 旅行照片 | 本地图片选择与拖放、缩略图、顺序调整和移除。 |
| 文件设置 | 自定义正文路径及已有项目照片引用，默认折叠。 |

日期、国家 / 地区、目的地和日记标题为必填项。国家显示名称随国家选择填入，允许自定义；留空时使用国家目录名称。其他字段为选填，字段定义见下文。

地点字段支持关联候选和可靠补全。选择国家后，行政区、目的地和类型候选会按当前地点范围收窄。中国目的地会优先从 `assets/catalogs/china-locations.json` 反查省级行政区，支持省略常见的“市”“县”等后缀，例如填写“衡阳”或“衡阳市”都会补全“湖南省”，填写“大理市”或“建水县”会补全“云南省”。跨省重名地点在无法唯一判断时不会强行填写。目录外地点继续使用个人历史记录补全；新地点仅根据明确后缀判断类型，例如中国的“省”“自治区”“直辖市”、日本的“都 / 道 / 府 / 県”，以及“市”“岛”“群岛”“国家公园”。自动填写的内容可直接修改，手工改动后不会再被覆盖。

旅行标识用于把多篇日记归入同一次旅行。编辑器会优先根据完整日期和目的地自动填写，未填写目的地时回退到行政区，格式为 `YYYY-MM-DD-pinyin`，例如 `2026-09-07-hengyang`。日期或地点变化时，尚未手工修改的自动值会同步更新；手工修改后不再覆盖。下拉候选按最近日期倒序列出 5 个不同的已有行程，便于同一次旅行的后续日记沿用标识。保存时，手工输入的中文标识也会转成小写、无声调拼音。「文件设置」中的正文路径会根据日期和目的地自动填写，并在尚未手工修改时同步更新；照片目录继续显示自动路径预览。

单行字段最多 200 字符，正文最多 100000 字符；已有照片列表最多 1000 项，每个文件名最多 200 字符。可选择 JPEG、PNG、GIF 和 WebP 图片，应用不另设张数或文件大小上限；实际容量取决于浏览器内存、磁盘空间和本机读写速度。

「保存旅行记录」创建正文并更新旅行索引；「保存修改」更新当前记录及正文。成功后页面重新加载记录与统计。线上内容更新需提交并推送相关文件。

日记详情的「修改」「删除」均需服务端口令验证。删除需再次确认，会移除记录及正文，保留照片文件；正文加载失败时不能修改，但仍可删除记录。操作是否可用由当前站点的写入 API 和登录会话决定：默认 localhost 可写；显式启用 remote write mode 后，同站点远程页面也可写；静态部署保持只读。更新认证配置、服务代码或写入模式后需重启进程。

### 正文视图与草稿

| 操作 | 输出或行为 |
| --- | --- |
| 源码 | 直接编辑带语法高亮的完整 Markdown，第一行一级标题与日记标题字段同步。 |
| 预览 | 在渲染结果上直接修改文字；工具栏支持粗体、斜体、标题、段落和列表。 |
| 导出草稿 | 下载 ZIP 草稿；`draft.json` 包含字段，所选图片保存在 `photos/` 中。 |
| 导入草稿 | 读取 ZIP 或旧版 JSON 草稿并填入表单，核对后另行保存。 |
| 清空编辑器 | 确认后清除表单、正文和待保存照片，可直接导入另一份草稿；不会删除已保存文件。 |

源码与预览双向同步，切换视图保留已输入内容。预览中选中文字后可设置格式，支持浏览器原生撤销与重做；粘贴内容按纯文本插入。键盘方向键、Home 和 End 可切换正文标签。预览修改后会按支持的 Markdown 结构重新序列化，空行和样式标记可能规范化；表格、代码块和嵌套列表等不支持的结构应保留在源码中编辑。

ZIP 草稿中的 `draft.json` 不是旅行索引，不能替换 `data/travel_data.json`。所选照片以独立文件存放在 ZIP 中，导入后恢复原图和顺序；已有项目照片仍依赖原路径。编辑器也兼容旧版 v1 至 v3 JSON 草稿，仅 v1 草稿自动补齐后来新增的可选字段。当前有未保存内容时，先导出草稿，再清空编辑器后导入。修改模式下导入草稿仍用于更新当前记录，保存前请核对窗口标题。

未保存草稿仅保留在当前页面内存中。关闭后重新打开同一记录可继续编辑；切换记录时，需确认丢弃未保存内容。刷新或离开页面前应保存或导出草稿。

### 正文路径与照片引用

新增记录的正文路径会自动按以下格式填写，仍可按需修改或留空使用保存端生成的默认值：

```text
data/travel-diary/YYYY/YYYY-MM-DD-pinyin.md
```

目的地会去除常见行政区后缀并转成小写、无声调拼音，例如“苏州市”默认生成 `data/travel-diary/2026/2026-09-11-suzhou.md`，“重庆市”生成 `2026-09-11-chongqing.md`。自定义路径必须保留与旅行日期一致的年份目录和日期前缀。文件名、照片目录和照片文件名仅允许 ASCII 字母、数字、连字符、下划线和点，禁止路径穿越和系统保留名称。新增记录不会覆盖已有正文；相同路径、元数据和正文的重复提交返回已保存状态。修改记录可替换自己的正文，但不能覆盖另一篇日记。修改日期时，需同步调整原正文路径或将其留空。

「选择照片」支持多选，也可将图片拖入指定区域。缩略图下方可调整顺序或移除照片。保存记录前，所选图片只保留在当前浏览器页面中。

保存时，新照片自动写入 `data/photos/pinyin/`。文件名主体由原文件名转成小写、无声调拼音，扩展名以实际图片格式为准；与本次照片列表重名时追加 `-2`、`-3` 等序号；若仍与磁盘上的其他文件重名，保存会拒绝覆盖，请调整文件名后重试。应用会自动填写 `photo_folder` 和 `photos`，顺序与缩略图一致。原始图片字节保持不变，不会压缩或裁剪。

「文件设置」中的照片目录和列表用于引用项目中已经存在的文件，照片目录限定在 `data/photos/` 下。存在新选择的照片时，已有照片会按需复制到目的地目录并排在新照片之前，原文件保持不变；若来源就是该目的地目录则直接复用。仅引用已有照片时不创建新目录。

保存失败会清理本次创建的照片文件与空目录。新增请求结果不确定时，可使用原草稿重试；修改或删除结果不确定时，先刷新核对记录，避免对旧内容再次操作。

### 全部数据导入与导出

个人主页右侧「数据备份」提供以下操作：

- 「导出全部数据」先在服务端验证访问口令，然后下载 `travel-diary-data-YYYY-MM-DD.zip`。动态备份即时包含磁盘上的 `data/` 与 `.secrets/auth.json`；后者只有 `scrypt` 哈希、随机盐、参数和口令策略，不含明文口令。服务端拒绝未登录的直接下载请求。
- 「导入全部数据」要求有效的 `HttpOnly` 登录会话和对应的 `X-Travel-Token`。服务端校验 ZIP 完整性与路径、旅行索引 JSON、记录字段和日期、正文路径与 UTF-8 内容、照片目录及引用、认证配置，并拒绝文件或父目录大小写冲突、文件与目录重名的路径；全部通过后才在同一数据锁内替换 `data/` 与 `.secrets/`，任一步失败都会恢复原目录。local 和 remote write mode 使用同一导入安全检查。

备份中的认证配置不负责授权本次导入：只有当前服务签发的登录会话才能覆盖数据。导入带 `.secrets/auth.json` 的完整备份后，会恢复备份时的访问口令，并立即注销所有旧会话；随后需要用备份对应的口令重新登录。旧备份没有认证配置时会保留服务器当前配置；旧 `data/password.json` 会被丢弃，不会重新发布明文密码。remote 模式还会拒绝恢复标记为非生产级的弱认证配置，避免导入后降低安全等级。

通用静态服务器需要先运行 `npm run data:archive`，再把 `dist/travel-diary-data.zip` 作为站点根目录的 `travel-diary-data.zip` 发布。静态服务器没有后端，无法安全校验口令，所以构建时 ZIP 只包含本来就会公开的 `data/`，明确不含 `.secrets/auth.json`，且不能导入。使用本项目服务器并登录后，本机或 remote 模式远程页面都可导入完整备份；操作前务必导出当前备份。校验失败不会修改现有数据。ZIP 使用标准 UTF-8 文件名和无加密存储格式，得到动态完整 ZIP 的人可以离线猜测其中的密码哈希，应像保护私密数据一样保护备份。

### 静态托管与离线使用

| 环境 | 编辑与导出 | 保存到项目文件 |
| --- | --- | --- |
| 本机 `npm start` 与 localhost 地址 | 支持，断网可用 | 支持，默认 local write mode |
| `--network --write-mode=local` 的远程地址 | 支持编辑、草稿与静态备份导出 | 不支持，能力探测后进入只读模式 |
| `--network --write-mode=remote` 的局域网或同站点域名 | 登录后支持含认证配置的动态导出 | 支持新增、修改、删除和全量导入 |
| GitHub Pages 或通用静态服务器 | 页面资源加载后支持 | 不支持，写入 API 不存在 |

只读环境仍可编辑记录、选择照片并导出 ZIP 草稿，也可下载当前站点只含公开 `data/` 的静态数据备份。要写回项目文件，请在任一已启用写入 API 的站点导入草稿，核对后保存。草稿或数据导出不会修改站点，也不会触发发布。

远程部署示例：

```bash
npm run auth:set
node js/server.js --network --write-mode=remote
```

局域网可通过 `http://192.168.1.100:9000/` 使用，但 HTTP Cookie 不带 `Secure`，只适合受信网络。生产部署应让 Nginx、Caddy、Apache、Cloudflare Tunnel 等把 `https://example.com/` 代理到 Node 的 HTTP 端口，并优先用 `--local --write-mode=remote` 使 Node 只接受同机代理连接；服务端根据经过同源校验的 HTTPS `Origin` 签发 `Secure` Cookie，不信任 `X-Forwarded-*`。API 使用相对 URL，代理必须保留外部 Host，并建议在应用认证外再增加 VPN、Zero Trust 或上游身份验证。

本项目的离线运行依赖本机服务器与仓库内资源。线上页面未配置 Service Worker 缓存，不保证断网后的首次访问或刷新可用。

保存失败时表单内容保持不变。若请求超时，服务器可能已完成写入，应使用原路径和原内容重试。数据文件损坏、权限异常及写入锁恢复参见 [维护与发布指南](MAINTENANCE.md#写入故障恢复)。

### 手工新增

1. 在 `data/travel-diary/YYYY/` 新建 Markdown 文件。
2. 在 `data/travel_data.json` 添加一条记录。
3. 运行 `npm test`。
4. 启动 `npm start`，在浏览器检查首页、旅行路径和日记详情。

推荐文件名：

```text
data/travel-diary/YYYY/YYYY-MM-DD-slug.md
```

示例：

```text
data/travel-diary/2026/2026-07-11-suzhou.md
```

## 元数据字段

`data/travel_data.json` 是数组，每一项代表一篇旅行日记。

| 字段 | 类型 | 必需 | 说明 |
| --- | --- | --- | --- |
| `date` | string | 是 | 日期，格式为 `YYYY-MM-DD`。 |
| `country` | string | 是 | 面向读者显示的国家或地区名称。 |
| `country_code` | string | 是 | ISO 3166-1 alpha-2 两位代码，用作稳定的国家标识，例如 `CN`、`US`、`JP`。 |
| `admin_area` | string | 否 | 一级行政区名称。可表示州、省、大区、都道府县、自治区等；城市国家或不需要该层级时可以省略。 |
| `admin_area_type` | string | 否 | 一级行政区类型覆盖值，例如 `州`、`省`、`都`。常见国家会自动提供界面标签，只在需要更精确说明时填写。 |
| `locality` | string | 是 | 实际目的地，不限于城市，也可以是村镇、岛屿、景区或其他地点。 |
| `locality_type` | string | 否 | 目的地类型，例如 `城市`、`岛屿`、`国家公园`。 |
| `trip_id` | string | 否 | 小写拼音旅行标识。编辑器默认按完整日期和目的地自动填写；同一次旅行包含多篇日记或多个目的地时，应从最近行程候选选择同一个值，用于按旅行去重计算到访次数。 |
| `desc_md` | string | 是 | Markdown 正文路径，相对项目根目录。 |
| `photo_folder` | string | 否 | 照片目录，相对项目根目录。 |
| `photos` | string[] | 否 | 照片文件名列表，与 `photo_folder` 拼接成图片路径。 |

示例：

```json
{
  "date": "2026-07-11",
  "country": "中国",
  "country_code": "CN",
  "admin_area": "江苏省",
  "locality": "苏州市",
  "trip_id": "2026-07-11-suzhou",
  "desc_md": "data/travel-diary/2026/2026-07-11-suzhou.md",
  "photo_folder": "data/photos/suzhou",
  "photos": ["canal.jpg", "garden.jpg"]
}
```

每篇记录都会按日期从早到晚获得行程编号，最早的行程为 1；记录卡片右侧和日记详情会显示同色同号的“行程”色签。如果同一次旅行去了同一省的多座城市，应为这些记录填写相同的 `trip_id`。例如南京和苏州属于同一次江苏旅行时，两篇记录都填写 `"trip_id": "2024-11-jiangsu"`，它们会共用同一个行程编号，并将江苏省计算为 1 次到访。色签编号仅用于界面分组，不展示原始 `trip_id`；未填写 `trip_id` 的旧记录会各自获得独立编号。

## 不同国家和特殊地区

一级行政区统一写入 `admin_area`，界面会根据 `country_code` 使用适合该国家的名称。例如美国显示“州 / 特区”，日本显示“都道府县”，加拿大显示“省 / 地区”；未配置的国家回退为“一级行政区”。

美国州：

```json
{
  "country": "美国",
  "country_code": "US",
  "admin_area": "California",
  "admin_area_type": "州",
  "locality": "San Francisco"
}
```

日本都道府县：

```json
{
  "country": "日本",
  "country_code": "JP",
  "admin_area": "東京都",
  "locality": "東京"
}
```

城市国家可以省略 `admin_area`：

```json
{
  "country": "新加坡",
  "country_code": "SG",
  "locality": "新加坡"
}
```

系统仍能读取旧内容中的 `province` 和 `city`，旧版 `province/city` 路由也会自动转换；新增内容应统一使用新字段。

## 国家目录

`assets/catalogs/countries.json` 是应用使用的通用国家目录，与个人旅行记录分开维护，当前包含 ISO 3166-1 的 249 个国家、属地及特殊地理区域。每一项包含：

- `code`：ISO alpha-2，两位代码。
- `alpha3`：ISO alpha-3，三位代码。
- `numeric`：ISO 三位数字代码。
- `name_zh`、`name_en`：Unicode CLDR 提供的简体中文和英文名称。
- `aliases`：常用简称或名称变体，可用于旧内容兼容和国家识别。
- `admin_area_label`、`admin_area_option`：一级行政区在界面中的称谓。
- `admin_area_optional`：该国家或区域是否通常可以省略一级行政区。

旅行记录中的 `country_code` 必须能在该目录中找到。常见行政体系会显示具体称谓，例如“州 / 特区”“省 / 地区”“都道府县”“酋长国”；未单独配置的国家统一回退为“一级行政区”，不会错误地假设为省。

国家目录由 `scripts/update-countries.mjs` 生成。需要同步 Unicode CLDR 数据时：

```bash
npm run countries
npm test
```

生成脚本固定 CLDR 版本，避免每次安装或启动时访问外部网络。不要直接在运行时代码中新增国家表。

## 中国省市区目录

`assets/catalogs/china-locations.json` 保存中国大陆 31 个省级行政区，以及对应的地级目的地和区县名称。新增记录时仅当 `country_code` 为 `CN` 才会使用该目录：

- 根据目的地唯一反查 `admin_area` 和 `admin_area_type`。
- 在行政区和目的地下拉候选中补充完整省、市信息，个人历史记录仍排在前面。
- 同名地点对应多个省份时保持为空，等待手工选择行政区。
- 香港、澳门和台湾继续按国家目录中的 `HK`、`MO`、`TW` 独立处理。

目录由 `scripts/update-china-locations.mjs` 从固定版本的 `cn-division` 生成，数据来源与许可信息记录在目录元数据及 `THIRD_PARTY_NOTICES.md` 中。需要更新时运行：

```bash
npm run china-locations
npm test
```

生成结果会随仓库分发，页面运行时不访问外部服务，因此离线新增记录仍可使用自动补全。

## Markdown 写法

正文建议以一级标题开头：

```markdown
# 苏州一日

## 平江路

雨后的石板路很安静，沿河的茶馆开得很早。

- 适合步行
- 适合拍照
- 傍晚灯光更好
```

当前解析器支持：

- `#` 到 `######` 标题。
- `- ` 无序列表。
- 段落和换行。
- 行内链接、粗体、斜体、删除线、标记、上标、下标和行内代码。

当前解析器不支持表格、代码块、HTML 块和嵌套列表；需要这些能力时，应先扩展 `js/data.js` 并补充测试。

## 照片

没有照片时可省略 `photo_folder` 和 `photos`，也可保留空列表：

```json
"photo_folder": "data/photos/suzhou",
"photos": []
```

如果添加照片，建议创建：

```text
data/photos/suzhou/
├── canal.jpg
└── garden.jpg
```

然后在记录中写：

```json
"photos": ["canal.jpg", "garden.jpg"]
```

图片文件名使用小写英文、数字和连字符，避免空格与中文文件名，便于部署到静态托管平台。

## 内容检查

提交前检查：

- `desc_md` 指向的 Markdown 文件存在。
- `photos` 中每个文件都存在于 `photo_folder`。
- 日期格式为 `YYYY-MM-DD`。
- `country_code` 是有效的两位大写代码。
- `locality` 已填写；`admin_area` 是否填写应以当地行政层级为准，不要为了满足层级而重复国家名。
- 同一次旅行的多篇记录使用完全相同的 `trip_id`，不同旅行不要复用同一标识。
- 同一天多篇日记时，文件名 slug 必须不同。
- 运行 `npm test` 通过。
